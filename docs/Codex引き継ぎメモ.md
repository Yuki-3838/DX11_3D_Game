## 3. Issue G(直近の実装)の詳細 — ここが次の作業の土台

### やったこと
攻撃の時間・威力の定義が2箇所に重複していて、しかも値が食い違っていた:
- `gameobject/enemy.h`: 敵AIの状態遷移(=プレイヤーが見るアニメーションの長さ) `WINDUP_SECONDS = 0.80f`
- `system/OneVsOneCombat.h`: 実際のダメージ判定タイミング `ENEMY_WINDUP = 0.72f`

→ **予備動作アニメーションが終わる前に攻撃判定が始まっていた**(80msのズレ)。
これは「予兆を見てから回避を決める」という本作の核を直接壊すので、統合と同時に解消した。

新規ファイル **`system/CombatAttackTable.h`** を唯一の定義元とし、両者がここを参照する形にした。

```
namespace Combat {
  namespace Tuning { /* constexprな数値。クラス内のstatic constexprから使う */ }
  const AttackData& PlayerWeakAttack();   // AttackData形式でも取得できる
  const AttackData& PlayerHeavyAttack();
  const AttackData& EnemyBasicAttack();
}
```

- `Tuning`名前空間の`inline constexpr`値 … `static constexpr`メンバが必要な既存コードから使う
- `AttackData`を返す関数 … 攻撃を「種類」として扱いたい今後の実装(Issue H)から使う
  (`Combat::AttackData`は`std::string`を含むためconstexprにできない。だから2層構造にしている)

### 意図的な挙動変更(1点のみ)
敵の予兆時間を **0.72秒 → 0.80秒に統一**(長い方に合わせた)。攻撃判定がアニメより先に出ないようにするため。
それ以外は純粋なリファクタで、数値・挙動は変えていない。

<details>
<summary>実装前に書いた検討メモ(参考)</summary>

#### 当初の検討: 敵の攻撃パターンを2〜3種類に増やす
**目的**: 攻撃が1種類しかない今は「待てば必ず同じことが起きる」ので、実質的に読み合いが成立しない。
複数の攻撃候補があって初めて「これは踏み込める/これは危ない」という判断が生まれる。

**現状の構造(実装前に把握すべきこと)**:
- 敵AIは `gameobject/enemy.cpp` の`update()`にあるステートマシン。
  `Approach→Circle→Windup→Active→Recovery→Retreat` の一本道で、攻撃の種類という概念がまだ無い。
  `Windup`へ遷移する箇所は`update()`の冒頭付近(距離条件)にある。
- 攻撃の時間は `enemy.h` の`WINDUP_SECONDS`/`ACTIVE_SECONDS`/`RECOVERY_SECONDS`(現在は`Combat::Tuning`を参照する定数)。
  攻撃種別ごとに変えるなら、これらの`static constexpr`をやめて、
  「今選択中の攻撃のAttackData」をメンバに保持して参照する形へ変える必要がある。
- ダメージ判定は `system/OneVsOneCombat.cpp` の`Update()`内、`m_enemyAttack`まわり。
  こちらも`ENEMY_WINDUP`等の定数参照をやめ、敵が選んだ攻撃のAttackDataを受け取る形にする必要がある
  (`Update()`の引数追加、またはOneVsOneCombat側に「今の敵の攻撃」をセットする関数を足す)。
- 敵のアニメーション選択は `scene/GameScene.cpp` の`UpdateEnemyAnimation()`。
  現在は`GetAnimation("attack", 0)`の1本だけを`m_enemyAttackAnimation`に読み込んでいる(1487行目付近)。
  攻撃種別ごとにクリップを分けるならここも要変更。ただし**新しいモーションアセットは無い**ので、
  当面は同じクリップの再生速度や適用範囲を変えるなど、アセット追加なしで差を出す方針が現実的。

**推奨する実装順序**:
1. `CombatAttackTable.h`へ攻撃を2〜3種類定義する(例: 短い予兆の突き / 長い予兆の薙ぎ払い)。
   ダメージ・射程・各フェーズ長を変えて、「見てから対応を変える」意味が出るようにする。
2. `enemy`に「今選択中の攻撃」を保持させ、Windup遷移時に選ぶ(距離や乱数で分岐)。
   時間定数の参照を、選択中AttackDataの参照へ置き換える。
3. `OneVsOneCombat`が敵の選択した攻撃データを見てダメージ・射程・タイミングを決めるようにする。
4. HUD(`GameScene::DrawGameplayHud()`)の「INCOMING!」表示を、攻撃種別で文言・色を変えられるようにすると読み合いが分かりやすくなる。

**受け入れ条件**: プレイテストで「来る攻撃によって対応(回避 or 踏み込み)を変える」判断が発生すること。

### 実機の見た目を確認する手順(重要 — コードだけで判断しないこと)

このプロジェクトは長らくコードだけを見て調整していたため、実際には破綻している変更を
「完了」と判断してしまうことが複数回あった。モーションや見た目に関わる変更をしたら、必ず実機を見ること。

PowerShellでゲームを起動し、ウィンドウをキャプチャできる。要点:
- ウィンドウは**タイトルではなく、プロセス内で最大のクライアント領域**で特定する
  (ImGuiのビューポート機能により、デバッグ窓が別のOSウィンドウとして複数存在するため、
   `MainWindowHandle`は小さなImGui窓を返すことがある)。
- `SetForegroundWindow`は単体では効かない(Windowsがバックグラウンドプロセスからの前面化を制限する)。
  `AttachThreadInput`で対象ウィンドウの入力スレッドへアタッチしてから呼ぶ必要がある。
  これをしないと、画面には別のアプリが写ったまま撮れてしまう。
- `.ps1`をUTF-8(BOMなし)で保存すると、PowerShell 5.1がShift-JISとして読んで日本語コメントが化け、
  C#のソース文字列まで壊れる。**スクリプトはASCIIのみで書くか、BOM付きで保存する**こと。
- 起動後、敵の登場演出が終わるまで10秒程度待つ。演出中は入力を受け付けない。

### 脚が静止する問題 … **解決済み(レイヤー合成 + 腰の沈み込み)**

`CAnimationMesh::UpdateLayeredAnimation()`で、下半身は移動・待機クリップ、上半身は攻撃クリップ、
という分担にした。攻撃中も脚が動き続け、「歩きながら攻撃」もこの構造で表現できる。

**腰(pelvis)は動かしていない**。沈み込みを平行移動で再現しようとして3回失敗したので、
安易に再挑戦しないこと。踏んだ罠を全部残しておく:
- **回転を含めると**キャラクター全体が傾いて寝転んだ姿勢になる。
  腰の回転はキャラクターの向きそのもので、クリップとモデルの基準姿勢が一致しないため。
- **水平成分を含めると**足が滑る(ワールド移動はゲーム側が管理しているため)。
- **単位が違う**(FBXはcm単位のことが多い)。差分をそのまま足すと桁違いになり地面へ埋まる。
- 安全な範囲(腰の高さの±12%)まで抑えると、今度は**脚の角度に見合う沈み込みが足りず、
  宙に浮いて脚をばたつかせたような姿勢**になる。

結論: **腰を正しく動かすには脚のIKで接地を保つ仕組みが要る**。それ無しに平行移動だけで
辻褄を合わせるのは無理だった。`ApplyAnimationToBones`の`translationBone`引数は残してあるが、
現在どこからも指定していない。

現在の構成:
- 立ち止まっている間は脚を動かさない(待機・攻撃とも休止姿勢。両者同じなので継ぎ目が出ない)
- 歩行・走行中は移動クリップが脚を動かす(腰の上下が小さく破綻しない)
- **移動中の攻撃はレイヤー合成が有効**(下半身=移動クリップ、上半身=攻撃クリップ)

現在、攻撃モーションから脚のボーンを除外している(`system/CCharacterAnimator.cpp`の取り込み条件)。
一度は脚も含めたが、**キャラクターが座り込んだように脚が開いて崩れた**(実機キャプチャで確認)。

**原因**: 脚だけをクリップで動かし、腰(hips)を固定しているため。
Mixamoのクリップの脚の回転は「腰も一緒に回転し、上下に沈む」前提で作られている。
ところが`system/CAnimationMesh.cpp:986`付近の実装は**平行移動を常にレスト姿勢へ固定**しており、
腰が沈まないまま脚だけが沈んだ姿勢用の角度を取るため、脚が横へ開く。

**根本解決の方針**: 攻撃クリップに限り、腰(hips)の回転と**平行移動(特に上下)**を取り込めるようにする。
ただしワールド位置はゲーム側(SRT)が管理しているため、腰の平行移動は
「レスト姿勢からの相対オフセット」として扱う必要がある(絶対座標をそのまま入れると二重移動になる)。
これができれば脚も含められ、踏み込みと体重移動が出せる。

### 見た目の品質(実機キャプチャで確認済み)

1. ~~**カメラが遠い**~~ … **対応済み**。攻撃中は基準距離の0.62倍へ寄せる
   (`GameScene::UpdateCombatCameraDistance()`)。実機で効果を確認済み。
   注視点(`m_targetHeight`)も下げる案は試したが、地面寄りを見る構図になり
   接近した敵に視界を塞がれるため取りやめた。距離だけを変えること。
2. ~~**影が無い**~~ … **対応済み(シャドウマッピング)**。当初は足元へ暗い円盤を敷く簡易接地影だったが、
   平行光源による本物の影へ置き換え済み。キャラクターの形がそのまま影になる。
   - 影の描画先・パス制御は`Renderer::BeginShadowPass()`/`EndShadowPass()`/`SetLightViewProjection()`。
   - 影を落とす対象は`GameScene::RenderShadowMap()`で描く(地面や壁は受け手なので描かない)。
   - 影の範囲・向きは`GameScene::BuildLightViewProjection()`。範囲を広げるほど影が粗くなる。
   - 定数バッファはb7、影テクスチャはt1、比較サンプラーはs1を使用。
3. **エフェクト**(一部対応) — カメラシェイク・ヒットフラッシュ・剣の軌跡・命中の火花は実装済み。
   土煙、火花のテクスチャ、モンハン風の斬撃跡(赤い斬り傷)は未対応。
   - 命中の火花: `system/HitEffect.h`(ヘッダのみ)。**命中ワールド座標と弾く向きだけ**を受け取るので、
     敵の攻撃や差し替えた武器にもそのまま使える。カメラへ正対する板を進行方向へ引き伸ばし、
     **先端を点・尾を幅広**にした彗星型にして線状に見せている(逆向きにすると木片に見える)。
     1粒につき芯と外側の輝きの2枚を加算で重ね、根元には放射状の光条10本を出す。
   - **ダメージ数値は出さない方針**(一度実装したがユーザー判断で削除済み)。
   - **テクスチャ無しでエフェクトを作るときの原則**(火花で全部踏んだ):
     - **加算合成にする**。半透明合成だと重ねても明るくならず色紙のように見える。
     - **四角い板をそのまま光らせない**。輪郭が箱として見える。
       放射する光条や、先端を点にした彗星型など、**辺が見えない形**にする。
     - **実寸を確認する**。キャラクターは約29単位。エフェクトが体長と同じ大きさだと板に見える。
     - **単色1枚にしない**。芯と外側の輝きの2層、色を寿命で変化、で立体感が出る。
   - **色でエフェクトのフレームを探すときは、他の演出との混同に注意**。
     被弾時の画面端の赤いビネットを火花と誤検出した。走査範囲から画面端を除くこと。
   - 剣の軌跡: `system/WeaponTrail.h`(ヘッダのみ)。
     **刃の根元と先端のワールド座標しか受け取らない**ため、剣やキャラクターのモデルに依存しない。
     この2点は`CAnimationMesh::GetSwordWorldSweep()`が武器ボーンから求めているので、
     `CharacterModelProfile`の`weaponBone`さえ解決できていればモデル差し替えでも動く。
     敵の武器に使う場合もインスタンスを1つ増やすだけでよい。
   - **加算する色は控えめにすること**。ヒットフラッシュは加算量0.85で敵全体が金色に潰れ、
     姿勢も予兆も読めなくなった。実機で見ながら0.16まで下げている。モデルが暗いほど影響が大きい。
   - **エフェクトが見えないときは、一時的に不透明の原色で強制描画して描画経路を切り分ける**。
     淡い色のまま原因を推測するより速い(実際にこれで軌跡の描画が正常だと分かった)。
   - カメラシェイク: `ThirdPersonCamera::TriggerShake()`。
     **揺れを含まない基準位置を別に持つこと**。指数補間は前フレームのカメラ位置を補間元にするため、
     揺れた位置を渡すと揺れが減衰せず残り続ける。
   - ヒットフラッシュ: 定数バッファ**b8**(`TintBuffer`)+ `Renderer::SetCharacterTint()`。
     メッシュのマテリアルは`CStaticMeshRenderer::Draw()`が**サブセットごとに設定する**ため、
     描画前にマテリアルを差し替える方法は使えない(上書きされる)。描画後は必ず0へ戻す。
   - 被弾時は画面の四辺だけを赤くする。**中央を覆わない**ので予兆が隠れない。
   - 強攻撃1.5倍・隙への一撃1.4倍で手応えを強めている(`GameScene`のヒット処理)。
4. **ライティングが平坦**(未対応) — 環境は無地、鎧と剣にハイライトが乗らない。
5. ~~**敵が密着するとカメラの視界を塞ぐ**~~ … **対応済み**。
   `GameScene::CalcEnemyOccludedCameraDistance()`で、注視点からカメラ側への線分と
   敵を近似した球の交差を解き、遮蔽していれば手前で止める。壁の判定と`min`を取って
   `SetCollisionDistance()`へ渡している。
   - 判定には**実際のカメラ位置と注視点**(`ThirdPersonCamera::GetPosition()/GetLookat()`)を使うこと。
     ロックオン時は注視点がプレイヤーと敵の中間寄りなので、理想的なブームを再計算すると構図とずれる。
   - 敵の半径は境界球ではなく胴体の太さ相当(ローカルAABBのX幅の40%)。
     尻尾や翼を含む球だと少し離れただけでカメラが寄ってしまう。
   - 限界: 球近似のため、細い首や尻尾だけが視界を横切る場合は反応しない。対象は先頭の敵のみ。

### 2026-09-09 敵カットシーン→戦闘の影と後ろ足の遷移修正

ユーザー報告: 「カットシーンから戦闘シーンに入るところで影が合っていない。後ろ足が上がっているかもしれない」。

### 2026-09-09 敵Idle→Walkの回転クロスフェード

フレーム0への即時リセットだけでは、カットシーン最後のIdle姿勢から戦闘開始のWalk姿勢へ切り替わる瞬間に、後ろ足が跳ねて見える可能性があるため追加実装した。

### 2026-09-09 壁が影を受けない問題

壁は`Box::DrawUnlit()`で描いているため、`unlitTexturePS.hlsl`が使われる。
このピクセルシェーダーだけ`CalcShadowFactor(In.ShadowCoord)`を呼んでおらず、床やキャラクターには影が出ても壁には影が出なかった。

`unlitTexturePS.hlsl`へシャドウ係数を追加した。`unlitTextureVS.hlsl`は既にライト空間の`ShadowCoord`を出力しているため、頂点側の変更は不要。
無照明は面の向きによる明暗を止めるためのもので、影の受け取りまで止めない方針にした。
壁を影生成パスへ追加する必要はない。壁は影を落とす側ではなく、影を受ける側だからである。
同じ無照明シェーダーを使う床や箱にも影が出るが、別シーンでは`ShadowParams.y`が無効になっていることを確認すること。

- **ビルド確認**: `MSBuild.exe DX11_3D_Game.sln /t:DX11_3D_Game /p:Configuration=Debug /p:Platform=x64`
  (MSBuildの場所例: `C:\Program Files\Microsoft Visual Studio\18\Enterprise\MSBuild\Current\Bin\MSBuild.exe`)
- **新規モーションアセットは追加できない**。手持ちのクリップの範囲で工夫する。

- **HLSLは実行時コンパイル**。C++のビルドが通ってもシェーダの構文エラーは検出されない。
  シェーダを触ったら必ず`fxc`で検証すること:
  `& "C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\fxc.exe" /T vs_5_0 /E main shader\<file>.hlsl`
  (ピクセルシェーダは `/T ps_5_0`)
- **シェーダは行ベクトル規約**(`mul(pos, M)`)。行列→クォータニオン変換などで
  一般的な列ベクトル規約の式をそのまま使うと符号が反転する。
- **実行時コンパイルは`D3DCOMPILE_ENABLE_STRICTNESS`付き**。`fxc`で検証するときは`/Ges`を付けること。
  付けないと再現しない不具合がある(実際にこれで「起動時に画面が真っ黒」を踏んだ)。
- **`PS_IN`(common.hlsl)へ要素を追加したら、それを出力する全ての頂点シェーダーと
  ジオメトリシェーダーで値を設定すること**。1つでも漏れると
  `variable 'output' used without having been completely initialized` でコンパイルに失敗する。
- **シェーダーの生成失敗は`MessageBox`でゲームが停止する**。キャプチャが真っ黒なときは、
  まずプロセスのウィンドウ一覧に "error" というダイアログが無いか確認すること
  (ダイアログの本文にファイル名と行番号が出る)。
- **敵は描画時にX軸へ+90度回転している**(`enemy::getRenderSRT()`。モデルが傾いた姿勢で作られているため)。
  この回転でローカル+Zがワールド-Yを向くので、接地の計算など「上下方向」を扱うときは
  **ローカルAABBのmin.yではなくmax.zを使う**こと。プレイヤーには回転補正が無いのでmin.yで正しい。
  同じ式を使い回すと敵が浮く(実際に踏んだ)。
- **MSBuildはエラーを標準出力(stdout)へ出す**。標準エラー(stderr)だけを見て
  「ビルド成功」と判断してはいけない。実際にこれでコンパイルエラーを見逃した。
  判定は**終了コード**と、出力から `": error"` を検索して行うこと:
  `$out = & $msbuild $sln /p:Configuration=Debug /p:Platform=x64 /nologo /v:minimal 2>&1`
  `$out | Where-Object { $_ -match ": error" }` と `$LASTEXITCODE` を必ず確認する。
- **スクリプトで機械的にコード片を削除しない**。一時的な調査コードを正規表現や
  ブレース対応で削除したところ、直前の変数宣言(`SRT srt{};`)まで巻き込んで消し、
  ビルドを壊した。削除は編集ツールで範囲を目視確認しながら行うこと。
- **実装したら`docs/実装ログ.md`とこのファイルの両方を更新する**。
  さらに、技術的な選定が発生した実装では、`docs/技術解説.md`または該当する専門資料
  (`docs/スキニング技術解説.md`など)にも、採用理由・採用しなかった代替案・利点・欠点・
  現時点の限界・検証結果を追記する。実装内容だけでなく、なぜその方式にしたかを後から
  説明できる状態を維持すること。

## 7. 敵の予兆(2026-09-10 実装) — この作品の核

**敵の攻撃モーションは`dragon_attack.dae`の1本しか無い**。攻撃が3種類あっても、
以前は再生速度が違うだけで見た目がほぼ同じだった。そのためプレイヤーが
「何が来るか」を知る手段はHUDの文字しか無く、「モンスターを見る」ではなく
「文字を読む」ゲームになっていた。これを次の形で解決している。

- **[system/EnemyAttackPose.h](../system/EnemyAttackPose.h)**(ヘッダのみ)が、
  攻撃の種類・段階・経過秒から体の傾き/ひねり/高さのずらし量を返す。
  - 叩き付け: 反り返って伸び上がる → 前へ叩き落とす
  - 噛みつき: 低く沈んで鼻先を落とす → 突っ込む
  - 薙ぎ払い: 体を横へひねる → 反対側へ振り抜く
- **適用先は`enemy::getRenderSRT()`だけ**。物理SRT・衝突・敵AIには入れないこと。
  演出とゲーム内の位置を混ぜると壁抜けや接地ずれを呼ぶ。
- **見た目を変えたら当たり判定も合わせること**。敵の攻撃判定は元々**距離だけ**で、
  真後ろでも当たっていた。今は`Combat::EnemyHitHalfAngleOf()`で正面からの角度を
  攻撃ごとに変えている(噛みつき35度/叩き付け55度/薙ぎ払い110度)。
  角度計算に渡す向きは**必ず物理SRT**の`rot.y`。描画用SRTには演出のひねりが入っている。
- **調整のしかた**: `dev_settings.ini`に`force_enemy_attack=slam|bite|sweep`と書くと
  その攻撃だけを出す。デバッグ表示の「Force enemy attack」でも切り替えられる。
  これが無いと狙った攻撃が出るまで待つことになり、構えを見比べられない。
- **実機で見比べること**。噛みつきの初期値(前傾0.20/沈み込み-3.4)は
  叩き付けと見分けが付かず、実機キャプチャで気付いて0.34/-7.5へ強めた。
  数値だけでは「区別できるかどうか」は判断できない。
- **溜めを大きくしすぎない**。クリップは1本のままなので、体だけ大きく動かすと
  手足が付いていかないのが目立つ。区別できる最小限に留める。

### 演出で本体を傾けたら、接地の計算も直すこと(2026-09-10 に踏んだ)

敵の接地は毎更新で**スキニング後の頂点**から最下点を求めている。
これは「X軸へ+90度回すとローカル+Zが下を向く」前提で、**Zの最大値**を使っていた。
構えの演出でピッチを足したらこの前提が崩れ、**攻撃のたびに敵が地面へ埋まった**。

- 現在は`CAnimationMesh::GetAnimatedLowestLocalHeight(extraPitch)`が
  追加ピッチ込みの最下点を返す。高さは `-y*sin(p) - z*cos(p)`(行ベクトル規約)。
  p=0で`-GetAnimatedLocalMaxZ()`に一致する。
- **姿勢オフセットに高さ(lift)を持たせてはいけない**。接地を毎更新でやり直しているので
  必ず食い違う。傾ければ接地側が最下点を追うため、沈み込みも伸び上がりも自然に付く。
- ヨーは高さに影響しないので自由に使える。

### 影の範囲はプレイヤー中心である(カットシーンは例外)

`BuildLightViewProjection()`の正射影は**プレイヤー中心・一辺260**。
限られた影マップ解像度を戦闘へ集中させるためだが、
**プレイヤーから130以上離れたものは影が切れる**。
登場カットシーンではカメラがドラゴンを映しプレイヤーは画面外にいるため、
着地点(z=-120)のドラゴンがはみ出して影が合っていなかった。
現在は`m_enemyIntroActive`の間だけドラゴン中心・一辺460にしている。
今後カメラが遠くを映す演出を足すときは、同じ問題が出ると考えること。

### 次の判断が要るところ

HUDは今も予兆中に攻撃名(`HEAVY SLAM`等)を出している。体の構えで読めるようになった今、
これを残すか(初見でも分かる)、消すか(モンハンのように体だけで読ませる)は
ゲームデザインの判断であり、ユーザーに確認してから変えること。

## 8. 他のPCで動かすための決まり(2026-09-10 確認)

- **クローン直後の状態でDebug|x64・Release|x64ともにビルドが通る**。実際にクローンして確認済み。
  依存を足す変更をしたら、この状態を壊していないか同じ手順で確かめること。
- **AssimpはDebugとReleaseで別のDLLをリンクしている**(`system/AssimpPerse.cpp`の`#ifdef _DEBUG`)。
  - Debug: `assimp-vc143-mtd.lib` / `assimp-vc143-mtd.dll`
  - Release: `assimp-vc142-mt.lib` / `assimp-vc142-mt.dll`
  - 理由: デバッグ版Assimpは`ucrtbased.dll` / `MSVCP140D.dll`という**デバッグ版CRT**へ依存する。
    これはVisual Studioが入っているPCにしか無く、再頒布も許可されていない。
    **Debug構成のビルドは絶対に配布しないこと**。
- **配布物を作るときは `MakeDistribution.bat`**。Release|x64をビルドし、
  実行ファイル・リリース版AssimpのDLL・`shader`・`assets`を`dist`へまとめる。
  - `dist`は約695MB。`assets`を丸ごとコピーしているため。減らすなら実際に読むモデルだけに絞る。
  - このバッチは**CP932(Shift-JIS)で保存すること**。UTF-8で保存すると`cmd`が行を壊し、
    「'…' is not recognized as an internal or external command」が並ぶ。
- **依存を疑うときは `dumpbin /dependents` を使う**。コードや資料の記述ではなく実物を見る。
  末尾が`D.dll`(`MSVCP140D.dll`, `VCRUNTIME140D.dll`, `ucrtbased.dll`)ならデバッグ版CRT依存。
- `third_party/DirectXTK/lib`(約110MB)と`third_party/assimp/bin`は**意図的に追跡していない**。
  DirectXTKは`SimpleMath`のヘッダしか使っておらず、`Matrix::Identity`等は
  `system/SimpleMathIdentity.cpp`で自前定義しているため`DirectXTK.lib`はリンクしていない。
  AssimpのDLLはリポジトリのルートにある。
- ローカル専用の`dev_settings.ini` / `audio_settings.ini`と、`dist/`は`.gitignore`に入れてある。

### 2026-09-09 戦闘カメラ第一段階

`system/ThirdPersonCamera.h/.cpp`と`scene/GameScene.h/.cpp`を更新した。

- 通常カメラとロックオンカメラの位置・注視点を指数補間し、敵の移動や攻撃中の寄り戻しを滑らかにした。
- ロックオン時はプレイヤー後方を維持し、両者の中間より少しプレイヤー側・高めを注視する。敵方向へ6単位の肩越しオフセットを加え、敵の全身と自分の回避方向を読みやすくしている。
- 敵との距離に応じた76〜112単位のフレーミング距離へ、攻撃中の`m_lookDistance`縮小率も掛ける。通常時だけズームする不具合を避けた。
- 登場演出の最後は`BeginBattleTransition()`で、カットシーンのカメラ位置・注視点から戦闘カメラへ0.36秒のsmoothstep遷移を行う。`Reset()`によるハードカットへ戻さないこと。
- 中央ボタンを押しながらマウスを動かすと通常時のカメラを周回できる。右クリックは強攻撃なのでカメラ操作には使わない。`GetYaw()`は周回分込みでプレイヤー移動に渡る。
- 再戦時は`m_cameraDistanceCurrent`を基準距離へ戻す。

採用理由は、プレイヤー後方の安定した操作感(Elden Ring寄り)と、敵との相対関係を常時画面へ残す構図(Monster Hunter寄り)を両立するため。完全な中間配置、即時カメラ切り替え、右ドラッグ操作は、プレイヤーが隠れる・画面が跳ねる・強攻撃と競合するため不採用。

制約: ロックオンは現在先頭の敵1体のみ。カメラ衝突は闘技場外周の円近似で、壁の角・個別遮蔽物のレイキャストではない。ロックオン中は手動周回より相対フレーミングを優先する。

検証: Debug|x64ビルド成功(終了コード0・エラー0)、修正版起動・プロセス応答確認済み。ゲーム本体の描画ウィンドウをキャプチャできない環境のため、遷移の実画面目視は継続確認する。

### 2026-09-10 攻撃開始・終了のアニメーション補間と歩行中攻撃

- 既存のキーフレーム`slerp`と下半身ロコモーション＋上半身攻撃のレイヤー構造を確認したうえで、足元を壊さない不足部分を実装した。
- `CAnimationMesh::CaptureCurrentLocalPose()`で現在のローカル姿勢を取得し、FBX攻撃の開始時に次の更新フレームで姿勢を保存する。攻撃上半身だけを0.10秒のsmoothstepで補間し、開始時の姿勢跳びを抑える。
- 攻撃終了時も攻撃姿勢から歩行・待機へ0.10秒で戻す。下半身は攻撃側へ補間しない。腰・ルート・足を全身攻撃から上書きして、再び埋まりや浮きが出る実装には戻さないこと。
- `CharacterAnimationState.deltaSeconds`を追加し、攻撃・歩行・待機の時間とフレーム進行を実時間に合わせた。
- `GameScene`ではW/A/S/D入力を保持している攻撃中だけ移動ロックを解除する。入力を離した攻撃中は、従来どおりその場攻撃になる。これで実際の操作でも歩きながら攻撃できる。
- `CAnimationMeshBlender`を新経路の中心にはしていない。現状は「現在姿勢から選択ボーンだけを補間する」制御が必要なため、`CAnimationMesh`側の局所補間を使う。
- 制約: 0.10秒は固定値、足IK未実装、歩行↔走行ブレンド未実装。歩行中攻撃の足接地や攻撃開始・終了の実画面確認は、ゲームを操作して継続確認する。
- 検証: `Debug|x64`ビルド終了コード0・エラー0、修正版ゲームのプロセス応答を確認済み。ゲーム本体の連続画面キャプチャは環境上取得できていない。

### 2026-09-10 密着攻撃時のプレイヤー巨大化修正

- スクリーンショットの症状を調査。プレイヤーのワールド`SRT.scale`は攻撃中に変更されておらず、初期値は`CharacterModelProfile.modelScale = (10,10,10)`のまま。
- 直接の原因候補は、攻撃クロスフェードでローカルボーン行列を回転・移動だけへ再構成し、バインド姿勢のスケールを落としていたこと。`CAnimationMesh`/`CCharacterAnimator`の補間をSRT補間へ変更し、スケールを各軸で保持・補間する。
- 二次原因として、ロックオン攻撃ズームが密着時にフレーミング距離76へ0.62倍を掛け、47.12単位まで寄っていた。`ThirdPersonCamera`へロックオン最低距離64を追加。遠距離の攻撃ズームは残す。
- ワールド倍率を攻撃中だけ変更する修正には戻さないこと。衝突、剣、影と表示倍率がずれるため。ボーン補間は要素別線形補間ではなく、SRT分解・回転`slerp`・スケール/移動線形補間を使う。
- 制約: 負スケール/せん断は未対応。カメラ最低距離64はプレイヤー寸法とFOVに依存する固定値。壁押し戻しが同時に起きる場合は別途確認。
- 検証: `Debug|x64`ビルド終了コード0・エラー0、修正版ゲーム起動・プロセス応答を確認済み。密着攻撃の連続画面キャプチャは未取得。

**次にやること**: 実機で敵に密着して弱攻撃・強攻撃を行い、攻撃開始時の倍率変化、カメラ距離、攻撃終了後の倍率復帰を確認する。まだ大きく見える場合は、プレイヤーSRTではなくカメラ衝突距離をログ表示して切り分ける。

### 2026-09-10 攻撃中の移動・回避中攻撃を禁止

- 現在仕様は「攻撃中はその場攻撃」。W/A/S/Dを押していても`GameScene::lockPlayerMovement`を有効にし、プレイヤーのワールド移動を許可しない。上半身攻撃＋下半身ロコモーションの姿勢合成は残すが、歩きながら攻撃の操作は無効。
- `playerDodgeActive = m_player->isDodging()`を攻撃入力より先に判定し、回避中の左/右クリックは`attackInput`/`heavyAttackInput`から除外する。回避中に攻撃モーション・攻撃判定だけが始まり、回避移動が残る状態を再発させない。
- 回避開始と同フレームの攻撃入力も、同じ入力ゲートで扱う。攻撃と回避を同時成立させないこと。
- `player::update()`は回避中に移動して早期returnするため、後段で速度を止めるだけでは不十分。攻撃開始前に入力を排他する必要がある。
- 次回変更で移動攻撃を再導入する場合は、今回の仕様確認を経てから別途設計する。回避中攻撃は、キャンセル仕様を明示しない限り許可しない。
- 検証: `Debug|x64`ビルド終了コード0・エラー0、修正版ゲーム起動・プロセス応答を確認済み。実機操作での最終確認項目は「攻撃中WASDで位置が変わらない」「回避中クリックで攻撃が始まらない」。
