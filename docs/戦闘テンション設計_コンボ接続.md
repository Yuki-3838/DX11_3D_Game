# 戦闘の「読み合い」設計 と 3段コンボ接続問題

対象ブランチ: `feature/hata-player-hp-stamina-hud`
目的: このゲームの核を「敵の攻撃の予兆を読み、踏み込むか回避するかを選ぶ、はらはら感」に置く。
その土台として、いま詰まっている「3段コンボが繋がらない」問題を根本から解消する。
この文書は設計担当(私)が状況を分析した結果で、実装をコーデックス側と分担するためのIssueリストを末尾に用意した。

---

## 1. デザイン原則(モンハンが強い理由の言語化)

モンハンの緊張感は次の3層が揃って初めて成立する。どれか1つでも欠けると「読み合い」は起きない。

1. **予兆(Tell)** — プレイヤーが見て/聞いて「これから何が来るか」を判別できること。
2. **決断(Decision)** — その予兆を見た結果、複数の妥当な選択肢(踏み込む/様子見/回避/ガード)があり、選択を誤ると明確に損をすること。
3. **結末(Consequence)** — 選択が当たれば大きく報われ(隙への大ダメージ、爽快な手応え)、外せば明確に罰を受ける(被弾、体勢崩し)こと。

現状のコードを読むと、**1番目の「予兆」が最も弱い**。これは後述の通り「モーションがうまくいっていない」ことと直結している。デザインとアニメーションは同じ問題の表裏なので、両方セットで設計する。

## 2. 現状分析(コードから確認した事実)

### 2.1 敵は攻撃が1種類しかない

[gameobject/enemy.h:12](../gameobject/enemy.h#L12) のステートは `Approach→Circle→Windup→Active→Recovery→Retreat` の一本道で、攻撃パターンは1つだけ([scene/GameScene.cpp:1488](../scene/GameScene.cpp#L1488) `GetAnimation("attack", 0)` のみ読み込み)。
「読み合い」は複数の攻撃候補があって初めて選択になる。今は「予兆が来たら硬直明けまで反応が固定」なので、極端に言えば読む必要がない。

### 2.2 Windup(予兆)とActive(判定)が同じ1本のクリップで、Recoveryだけ唐突にIdleへ戻る

[scene/GameScene.cpp:1065-1071](../scene/GameScene.cpp#L1065) を見ると、Windup/Activeは同じ`m_enemyAttackAnimation`を連続再生していて(遷移時にフレームを巻き戻さない設計は良い)、ここ自体は破綻していない。
しかし **Recoveryに入った瞬間、フレームが0に戻りIdleへ即切り替わる**([scene/GameScene.cpp:1040](../scene/GameScene.cpp#L1040))。実時間で最長の隙(`RECOVERY_SECONDS = 1.35秒`, [enemy.h:48](../gameobject/enemy.h#L48))が、見た目には「攻撃を出す前と全く同じ棒立ち」になる。
→ プレイヤーが最も報酬を得るべき瞬間(隙)が、画面上は無防備に見えない。これは「危険を読む」より深刻で、「チャンスが見えない」問題。

### 2.3 敵の移動量が2重に加算されるバグ

[gameobject/enemy.cpp:155-156](../gameobject/enemy.cpp#L155)

```cpp
m_srt.pos += m_move;
m_srt.pos += m_move;
```

`m_move` が2回加算されており、Approach/Circle/Retreatの実移動速度が意図の2倍になっている可能性が高い。間合い管理(=読み合いの前提となる距離感)に直接影響するため、設計以前にここは直しておきたい。(→ Issue Aで独立して切り出す)

### 2.4 プレイヤーの3段コンボが「繋がらない」根本原因

[system/CCharacterAnimator.cpp:277-301](../system/CCharacterAnimator.cpp#L277) が弱攻撃3段の実体。

- 各段は**別々に用意されたモーションクリップ**(`sword_shield_slash.motion` / `_3` / `_4`)を都度ロードし直している。共通の「構え」から始まって「構え」に戻る、という契約がクリップ間で保証されていない。
- 各段に固定の`torsoYaw`が振られている: 1段目 `-0.34`、2段目 `+0.42`、3段目 `-0.10`([CCharacterAnimator.cpp:286-288](../system/CCharacterAnimator.cpp#L286))。**左→右→左と符号が反転**しており、上半身が段ごとに反対方向へ捻じれる。
- この捻じりは[CCharacterAnimator.cpp:1198](../system/CCharacterAnimator.cpp#L1198) `ApplyAttackMotionDesign`が**脊椎(spine/spine01/spine02)と腕だけ**に手続き的に加算している。脚・腰は`StripAttackLowerBody()`([CCharacterAnimator.cpp:1209](../system/CCharacterAnimator.cpp#L1209))で攻撃中ずっと固定されたまま。
- 段の切り替え時は`BeginAttackBlend()`が直前の描画姿勢から**わずか0.08秒**でブレンドするだけ([CCharacterAnimator.h:191](../system/CCharacterAnimator.h#L191) `m_attackBlendDuration = 0.08f`)。

つまり「体重移動も脚の踏み替えもないまま、上半身だけが段ごとに逆方向へ高速で捻じれ直し、0.08秒でごまかす」構造になっている。これが「違和感」の正体で、モーション素材の質以前に **コンボ段間の姿勢契約(入り/抜けの向き・体重配分)が設計として存在しない** ことが根本原因。素材を差し替えても、この契約がない限り同じ違和感が再発する。

### 2.5 データ駆動の設計が既に一度書かれていて、使われていない

[DX11_3D_Game/DX11_3D_Game/CombatDesign.h](../DX11_3D_Game/DX11_3D_Game/CombatDesign.h) に `AttackData`(Anticipation/Active/Recovery/Cooldown/Commit、Hitbox/Hurtbox、trackingAngle等)という、まさに今回欲しいデータ構造がPhase 1として既に設計されている。ただし`Main.cpp`からは呼ばれておらず、実戦闘(`OneVsOneCombat`/`GameScene`)とは別系統のまま放置されている([docs/設計概要.md:33](./設計概要.md#L33)にも「再利用できる」と明記あり)。
→ ゼロから設計せず、**この構造を実戦闘側に持ち込んで一本化する**のが最短ルート。

## 3. コア設計: 「読み合い」を機能させるための追加要素

### 3.1 攻撃の見た目を「予兆・判定・隙」で完全に切り分ける(最優先)

敵1体・攻撃1種のままでも、まずこれだけで体感は大きく変わる。

- **予兆(Windup)専用の姿勢/カメラ寄り**: 現状は同一クリップの前半を予兆として流用しているが、予兆区間だけ僅かにタメの強調(スロー・溜め呼吸・武器の光/エフェクト)を入れて「これは来る」と誰でも分かるようにする。
- **隙(Recovery)専用モーション**: Idleに即戻すのをやめ、「攻撃をやりきって体勢を崩している」姿勢を最低1枚追加する。これがないと「読み合いの報酬」が画面に存在しないのと同じ。
- **音とHUDでの二重化**: 予兆入りで警告音/敵名パネルの縁を光らせる、隙入りでロックオンパネルに「CHANCE」等の表示を出す。視覚だけに頼らずマルチモーダルにするのはモンハンも徹底している部分。

### 3.2 攻撃パターンを最低2〜3種に増やし、「見極め」を成立させる

1種類しかない今は「待てば必ず同じことが起きる」ため、実質的にリズムゲーにしかならない。

- 例: `突き(短い予兆・低ダメージ・すぐ隙)` / `薙ぎ払い(長い予兆・広範囲・回避必須)` / `咆哮(ノーダメージだがガード不能・距離を取るべき)` の3種を`CombatDesign.h`の`AttackData`で定義。
- 各攻撃のWindup尺・Activeの形状(Hitbox定義)を変え、「同じ予兆モーションでも次に何が来るか」を序盤の数フレームで示唆できるよう、予兆モーションの分岐点(枝分かれ)を早めに置く。
- フェイント(予兆だけ出して不発に終わる)は本筋が安定してから追加候補とする(優先度は低)。

### 3.3 プレイヤー側のリスク/リターンをHUDと連動させる

実装中のHP/スタミナバー([scene/GameScene.cpp:1271](../scene/GameScene.cpp#L1271))に加えて:

- ~~被弾直前(数フレーム)の回避に「見切りボーナス」を付ける~~ … **見送り**。成功表示や追加報酬は入れず、回避そのものの無敵フレームとスタミナ消費で成立させる。
- 敵の隙(Recovery)中に攻撃を当てると明確なヒットストップ強調(既存の`TriggerHitStop`を隙中だけ長めに)で「読みが当たった」快感を強調する。

### 3.4 難易度/ペーシングのノブを一箇所にまとめる

`WINDUP_SECONDS`等が`enemy.h`にハードコードされている状態から、`AttackData`ベースの調整可能な値に寄せておくと、後で「予兆をどれだけ分かりやすくするか」の調整をコード変更なしで試行できる。

## 4. アニメーション基盤の再設計(コンボ接続の根治)

### 4.1 「コンボ姿勢契約」を導入する

各コンボ段のモーションは以下を満たすことをルール化する:

- 全段が同じ**共通の構えポーズ(Guard Stance)**から始まり、同じ構えポーズに向けて収束する(完全一致でなくとも、股関節・胸の向きの差を±5°程度に収める)。
- 段をまたぐ`torsoYaw`は**符号を反転させない**。現在の`-0.34 → +0.42 → -0.10`のような往復ではなく、`-0.15 → -0.30 → -0.10`のように「同じ側に少しずつ捻る→最後に戻す」構成にする。
- この契約は`CCharacterAnimator.cpp`の`profiles[]`配列(287行目付近)を書き換えるだけで反映できるので、まず数値調整だけで体感差を確認できる。

### 4.2 下半身にも最低限の重心表現を持たせる

現状`StripAttackLowerBody()`で脚を完全固定しているため、3連撃でも脚は無反応。少なくとも:

- 段ごとに前後どちらかへの重心シフト(腰の`position`ではなく`rotation`の微小な前傾/踏み込み角)を1〜2個のボーンに procedural に加える(`ApplyAttackMotionDesign`と同じ手法を腰にも拡張)。
- 本格的な足IKは工数が大きいので後回しでよいが、「上半身だけがねじれるロボット感」を消すには腰の前傾だけでもかなり効く。

### 4.3 ブレンドを姿勢差に応じて可変にする

- 現在固定0.08秒のブレンドを、直前姿勢と次の開始姿勢の角度差に応じて0.05〜0.15秒程度で可変にする(差が大きいほど長く)。
- 可能であれば、Recovery(硬直)の後半とWindup(次の予備動作)の前半を短くクロスフェードし、「ピタッと止まってから次が始まる」機械的な継ぎ目を減らす。

### 4.4 データ駆動化: `CombatDesign.h`を実戦闘に統合する

- `OneVsOneCombat`が今ハードコードしている`PLAYER_WINDUP/ACTIVE/RECOVERY`等の定数群を、`Combat::AttackData`(既存・未使用)に置き換える。
- コンボの`profiles[]`もコード内配列ではなく`AttackData`のリストとして持たせ、モーション名・yaw予算・ブレンド時間をデータ側に寄せる。
- これにより「モーションを差し替えて試す」サイクルがコード修正なしで回せるようになり、コーデックス側にも作業を切り出しやすくなる。

### 4.5 ツール: コンボ連続プレビューをモーションエディタに追加

`scene/MotionEditorScene`に「1段→2段→3段を自動で連続再生するプレビューボタン」を追加し、実戦闘を起動しなくても継ぎ目を確認できるようにする。地味だが、この検証ループが無いと数値調整のたびにゲームを起動して確認することになり反復速度が落ちる。
