# スキニング技術解説 — LBS/DQSハイブリッドの採用理由

作品資料・技術説明用のドキュメント。
「何を実装したか」だけでなく「なぜその技術を選んだか」「他の手段では何が足りなかったか」を残す。

対象コード:
- `shader/vertexLightingOneSkinVSHybrid.hlsl` (実装本体)
- `shader/skinTransform.hlsli` (本体・影で共有するスキニング位置計算)
- `shader/shadowDepthSkinVS.hlsl` (影生成パス)
- `shader/vertexLightingOneSkinVSSafe.hlsl` (比較用に残した従来のLBS実装)

---

## 1. 何を実装したか(概要)

キャラクターのスキニング(ボーン変形)を、従来の **LBS(Linear Blend Skinning / 線形ブレンドスキニング)** 単独から、
**LBSとDQS(Dual Quaternion Skinning / デュアルクォータニオンスキニング)を頂点シェーダ内で両方計算し、
一定比率で混合するハイブリッド方式** へ変更した。

```
最終頂点位置 = lerp(LBSの結果, DQSの結果, DQS_BLEND)   // DQS_BLEND = 0.75
```

両方をGPU上で計算し、線形補間で混ぜている。混合比率はシェーダ内の定数
`DQS_BLEND`(0.0で完全なLBS、1.0で完全なDQS)で切り替えられる。

---

## 2. なぜ必要だったか(解決したかった具体的な問題)

### 発生していた症状
プレイヤーの攻撃モーションで、**上半身を大きく捻ると腕や胴の頂点が潰れて破綻する**。
このため、外部から取り込んだ攻撃モーションを全身に適用できず、
実際には「腕のチェーンだけにモーションを適用し、胴・腰・脚はゲーム側の静止姿勢で固定する」
という回避策を取っていた(`CCharacterAnimator::StripAttackLowerBody()` および
取り込みクリップのボーン制限)。

その結果、**攻撃が「棒立ちのまま腕だけ振っている」動き**になり、
モンスターハンターやエルデンリングのような全身の体重移動を表現できなかった。
つまりこれは見た目の好みの問題ではなく、**スキニング方式の制約がモーション表現の上限を決めていた**。

### 原因: LBSの数学的な性質
LBSは各ボーンの変換行列を重みで線形和する。

```
v' = Σ( w_i * M_i ) * v
```

行列を線形補間すると、**回転の補間としては正しくない**。
2つのボーンが互いに大きく捻れた(ねじれ角が大きい)状態では、
和の行列が回転行列でなくなり、頂点が回転軸方向へ吸い寄せられて体積が失われる。
これが一般に **キャンディラッパー(candy-wrapper)現象** と呼ばれる、
前腕の捻りや肩の回転で断面が紙のように潰れる破綻である。

LBSは「行列の線形和」という性質上、この破綻を**パラメータ調整では回避できない**。
ウェイト塗りを工夫すれば緩和はできるが、外部から取り込んだモーションに対して
モデル側のウェイトを毎回作り直すのは現実的ではなかった。

## 3. なぜDQS単独ではなくハイブリッドにしたか

### DQSの利点
DQSは各ボーンの剛体変換を**デュアルクォータニオン**(実部=回転、双対部=平行移動)で表し、
それらを線形結合してから正規化する。
クォータニオンは回転を単位球面上の点として扱うため、正規化を挟むことで
**結合結果が必ず剛体変換になる**。したがって捻っても体積が潰れない。
LBSの根本原因(回転が回転でなくなること)を、数学的に解消できる。

### DQS単独の欠点
一方でDQSには **バルジング(bulging / 関節の膨らみ)** という別の欠点がある。
肘や膝のように大きく「曲げる」関節では、内側の頂点が外へ張り出して不自然に膨らむ。
DQSは最短経路の剛体補間を行うため、LBSのように「潰れる」代わりに「膨らむ」方向へ誤差が出る。

### 両者の誤差は逆方向 → 混ぜると打ち消し合う

| 方式 | 捻り(twist) | 曲げ(bend) |
|---|---|---|
| LBS | 体積が**潰れる**(キャンディラッパー) | 比較的自然 |
| DQS | 体積を**保つ**(正しい) | 内側が**膨らむ** |

LBSとDQSは誤差の出る方向が逆なので、両者を混合すると
**捻りの潰れを大きく減らしつつ、曲げの膨らみも抑えられる**。
これが「どちらか一方」ではなくハイブリッドを選んだ理由である。
比率0.75はDQS寄り(捻りの改善を優先)で、曲げの膨らみが目立たない範囲として設定している。

## 4. 他の選択肢を検討した結果

| 選択肢 | 判断 | 理由 |
|---|---|---|
| **ウェイト塗りの調整で対処** | 不採用 | 根本原因(行列の線形和)が消えない。加えて外部から取り込むモーションごとにモデルのウェイトを作り直す必要があり、モーション差し替えの反復速度が落ちる。 |
| **捻り補助ボーン(twist bone)を追加** | 不採用 | 効果は高い実績ある手法だが、モデル側のリグ改変とウェイトの再配分が前提になる。使用しているモデルとMixamoリグの構成を変更する必要があり、作業量が本作の規模に見合わない。 |
| **DQSへ全面移行** | 不採用 | 捻りは解決するが曲げ関節の膨らみが新たに出る。片方の破綻を別の破綻に置き換えるだけになる。 |
| **Optimized CoR (Center of Rotation) スキニング** | 不採用 | 品質はDQSより高いが、頂点ごとの回転中心を事前計算する前処理パイプラインが必要になる。ランタイムだけで完結しないため、今回の構成では導入コストが見合わない。 |
| **LBS/DQSハイブリッド(採用)** | **採用** | シェーダ内で完結し、既存の定数バッファ構成・頂点フォーマット・モデルアセットを一切変更せずに導入できる。かつ両者の欠点が逆方向なので混合で相殺できる。 |

**採用の決め手**: 「アセットとパイプラインを変更せず、シェーダの変更だけで根本原因に対処できる」点。
既存の`BoneMatrix`定数バッファ(4x4行列配列)をそのまま使い、
**シェーダ内で行列からデュアルクォータニオンを復元**しているため、
CPU側の実装・データ構造・モデルデータには一切手を入れていない。

---

## 5. 実装上の技術的なポイント

### 5-1. 行列からデュアルクォータニオンを復元する
定数バッファのレイアウトを変えずに済ませるため、CPUからは従来どおり4x4行列を送り、
シェーダ側で回転クォータニオンを抽出している(`QuaternionFromMatrix`)。
本プロジェクトは **行ベクトル規約**(`pos = mul(pos, M)`)を採用しているため、
一般的な列ベクトル規約の抽出式とは非対角項の符号が逆になる点に注意して実装した。

平行移動は行ベクトル規約では第4行に入るため、`boneMatrix[3].xyz` から取得し、
双対部を `qd = 0.5 * (0, t) ⊗ qr` として構成している。

### 5-2. 反対称性(antipodality)への対処
クォータニオンは `q` と `-q` が同じ回転を表す。
符号がばらついたまま線形結合すると回転が打ち消し合い、頂点が破綻する。
そこで**最初に処理したボーンのクォータニオンを基準**とし、
内積が負になるボーンは符号を反転してから加算している。
DQSを実装する際に最も嵌まりやすい落とし穴であり、ここを外すと
特定の姿勢でだけモデルが弾け飛ぶという再現性の低いバグになる。

### 5-3. 既存の安全処理を両方の経路へ適用
元のLBSシェーダには次の2つの保護があり、ハイブリッド版でも維持している。

- **ボーンインデックスの範囲チェック**: FBXにはウェイトを持たない頂点(鎧の小物など)が混ざり、
  `BoneIndex = -1` をGPU配列へ渡すと不正参照でモデルが画面外へ飛ぶ。
- **ウェイト合計の補正**: 4ウェイトへ切り捨てた結果、合計が1未満になった頂点が縮む。
  不足分を恒等変換で補う。DQS側にも恒等デュアルクォータニオンで同じ補正を入れている。

### 5-4. 本体描画と影描画のスキニングを共有する

敵のカットシーンから戦闘への切り替えで、後ろ足の輪郭と影が合わない症状が出た。
調査すると、本体(`vertexLightingOneSkinVSHybrid.hlsl`)はLBS/DQSハイブリッドなのに、
影(`shadowDepthSkinVS.hlsl`)はLBSだけで頂点を変形していた。
ボーン行列の更新タイミングが同じでも、方式が違えば脚先の位置と輪郭がずれる。

そこで`SkinPositionHybrid()`を`shader/skinTransform.hlsli`へ切り出し、
本体と影の頂点シェーダーから同じ関数を呼ぶ構成にした。
これで次の処理が両パスで一致する。

- 4ウェイトのインデックス範囲チェック
- ウェイト合計が1未満のときの恒等変換による補正
- クォータニオンのantipodality対策
- `DQS_BLEND = 0.75`によるLBS/DQS混合

### 5-5. 他の方法を採用しなかった理由

| 方法 | 判断 | 利点 | 欠点 |
|---|---|---|---|
| 影だけLBSにする | 不採用 | 影の計算量が少なく変更も小さい | 本体と影の輪郭差が残る。さらに本体をLBSへ戻すと、ハイブリッド化で得た体積保持を失う |
| 本体と影へ同じ処理をコピーする | 不採用 | 共有ファイルなしで実装できる | DQS比率や安全処理の修正漏れが起きる。二重管理で再発しやすい |
| **共有includeで同じハイブリッドを使う** | **採用** | 本体と影の位置計算を一元化し、実装の不一致を構造的に防げる | 影でもクォータニオン計算を行うため、LBS単独よりGPU負荷が増える |

影にまでDQSを適用するのは、影の「質感」を上げるためではなく、
本体と同じ変形後シルエットから深度を作るためである。
なお、CPU側の敵接地推定は別経路のLBS近似なので、接地補正値まで完全に同一ではない。
法線も従来どおりボーン回転を反映していないため、影の一致と陰影の一致は別問題として残る。

### 5-6. カットシーンから戦闘へのアニメーション遷移

カットシーン中はIdle、終了後はWalkを選ぶが、遷移時にフレーム番号を共有すると、
Idleの途中の番号からWalkを開始して後ろ足だけが不連続に見える可能性がある。
そのため`GameScene::UpdateEnemyIntro()`の戦闘開始処理で、敵アニメーションのフレーム番号とtickを0へ戻す。

この方法は遷移時の状態だけを初期化するため、SRT・衝突・物理位置へ影響しない。
一方、これは敵のIdle→Walkだけを対象にした回転クロスフェードであり、任意のクリップ間を
自動で滑らかにつなぐ一般的な遷移ブレンド機構ではない。Walkの先頭姿勢と
カットシーン最後のIdle姿勢が大きく違う場合は、0.18秒では足位置の差を完全には隠せない。

### 5-7. カットシーンから戦闘への回転クロスフェード

上記の課題に対して、`CAnimationMesh::UpdateBlendedRotationAnimation()`を追加した。
遷移直前のIdle姿勢とWalkのフレーム0を同時にサンプリングし、共通ボーンの回転だけを0.18秒slerpする。
位置・スケールはWalk側を使うため、敵のワールド移動や描画接地補正と競合しない。

これはDQSの計算方式を変える実装ではなく、CPU側で作るボーンのローカル姿勢を遷移中だけ混ぜる実装である。
その後のGPUスキニングは通常フレームと同じLBS/DQSハイブリッドで、本体・影とも同じ`m_enemyBoneComb`を読む。

位置まで含めたポーズ補間を採用しなかったのは、ルートや腰の上下移動がSRT・接地補正と二重になり、
敵が地面へ埋まる既存の問題を再発させるためである。回転のみの方式は足裏を地面へ固定するIKではないため、
クリップ自体の接地ずれや、Idle終端とWalk先頭で足位置が大きく違う場合は完全には解決しない。

## 6. 効果と限界(正直な評価)

### 得られたもの
- 捻りを含む姿勢での体積の潰れが軽減され、**モーションを腕だけに制限する必要がなくなる**方向に進んだ。
  スキニング側の制約が外れたことで、全身モーションの適用を検討できる状態になった。

### 現時点での限界・今後の課題
1. **混合比率が固定値**: 現在は`DQS_BLEND = 0.75`のシェーダ定数。本来は
   「捻りが支配的な部位はDQS寄り、曲げが支配的な関節はLBS寄り」と**部位ごとに変えるのが理想**。
   頂点フォーマットに混合ウェイトを1つ追加すれば実現できるが、今回はメッシュ読み込み側の
   変更を避けるため見送っている。
2. ~~**法線がスキニングされていない**~~ … **対応済み**。
   以前は法線をワールド行列だけで変換しており、体を捻っても陰影が追従しなかった。
   `SkinVertexHybrid()`で**位置と法線を同じスキニングから**求めるようにした。
   DQSは剛体変換なので、混合した回転クォータニオンで法線を回すだけでよい。
   LBS側は行列の回転部分(3x3)のみを使う(法線は平行移動の影響を受けないため)。
   混合後は長さが崩れるので正規化する。
3. **スケールを含む変換には非対応**: デュアルクォータニオンは剛体変換(回転+平行移動)しか
   表現できない。ボーンにスケールアニメーションが入る場合、DQS側はそれを無視する。
   本作のモーションデータはスケールがほぼ1.0の固定であるため実害は出ていないが、
   スケールを使う演出を入れる場合はLBS側の比率を上げる等の対処が必要になる。
4. **定量的な計測は未実施**: 頂点シェーダの負荷増加(行列→クォータニオン変換が
   ボーンあたり1回発生する)は理屈上あるが、GPU時間の実測はまだ行っていない。

---

## 7. まとめ(面接などで一言で説明する場合)

> 攻撃モーションで上半身を大きく捻ると頂点が潰れる問題があり、
> 原因は線形ブレンドスキニングが「回転行列を線形和する」ために
> 結果が回転でなくなることでした。
> デュアルクォータニオンスキニングなら剛体変換として補間できるので捻りの潰れは解決しますが、
> 今度は曲げ関節が膨らみます。両者は誤差の出る方向が逆なので、
> 頂点シェーダで両方計算して混合するハイブリッド方式を採用しました。
> 定数バッファには従来どおり行列を送り、シェーダ内でデュアルクォータニオンへ変換しているので、
> CPU側のデータ構造もモデルアセットも変更せずに導入できています。

## 付録: 用語

- **LBS (Linear Blend Skinning)**: ボーン変換行列を重みで線形和する最も基本的なスキニング。
  高速で実装が簡単だが、捻りで体積が潰れる。
- **DQS (Dual Quaternion Skinning)**: 剛体変換をデュアルクォータニオンで表現し補間する方式。
  捻りに強いが曲げ関節が膨らむ。スケールは表現できない。
- **キャンディラッパー現象**: 捻り部位の断面が飴の包み紙のようにねじれて潰れるLBS特有の破綻。
- **バルジング**: 曲げ関節の内側が不自然に膨らむDQS特有の破綻。
- **反対称性(antipodality)**: `q`と`-q`が同一の回転を表すクォータニオンの性質。
  補間前に符号を揃えないと破綻の原因になる。
